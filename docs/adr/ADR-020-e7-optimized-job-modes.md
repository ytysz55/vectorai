# ADR-020 — E7 job-mode semantics and local UI boundary

- **Status:** Accepted for E7 UI-001
- **Context:** The E3 synchronous demo accepted four labels but routed `faithful` and `minimal` through the same unoptimized geometric pipeline. Advertising them as distinct modes would be misleading. E7 needs a review UI that follows the durable job contract rather than blocking on the legacy route.
- **Decision:** `/v1/jobs` accepts four modes. `geometric` uses the fast topology-checked baseline; `faithful` and `minimal` select their different E5 pinned optimizer profiles; `stroke` uses the stroke pipeline. The locked benchmark JSON is copied into the Python engine package as an offline runtime resource and CI compares it byte-for-byte to the benchmark source. `--optimizer-profiles` allows a local override; an unavailable profile prevents startup. Optimization failure falls back only as the explicitly reported `degraded` state. The legacy `/v1/vectorize` route remains an unoptimized compatibility demo and is **not** used by the E7 UI.
- **UI contract:** Upload only to loopback, poll `accepted`/`running` until terminal, display typed failures and cancellation, and show downloads/preview only for `success`, `degraded`, or `needs_review`. Reuse a pending idempotency key after a lost upload response for the same file/mode. In-progress jobs cannot silently start a duplicate when polling fails. Browser artifacts must match the local job ID and allowlisted path. Remove third-party font imports; no remote UI resources are needed.
- **Limits:** A successful E5 run proves profile routing, not that every image improves fidelity or compactness. The benchmark gates retain authority. The browser does not persist the active job ID across reloads, and binary wheel inclusion of the new JSON resource has not yet been verified on the current machine because the package build tool is unavailable. The local status record persists for manual recovery. Multi-process/multi-user deployment and hosted UI are out of scope.
- **Evidence:** `python/tests/test_job_modes.py` tests profile lock, engine routing and a two-mode HTTP run. `apps/web/tests/jobApi.test.mjs` covers all state gates, four mode labels, typed errors and artifact-path validation. Both are covered by the Python/web CI jobs. No real browser E2E run or Linux renderer parity is claimed.
- **Review trigger:** A bundled/installed wheel, hosted origin, new optimizer profiles, cross-session job UI, or mode-specific E8 performance/quality gates.
