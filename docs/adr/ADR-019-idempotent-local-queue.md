# ADR-019 — Bounded FIFO queue and private idempotency index

- **Status:** Accepted for E7 API-002
- **Context:** ADR-018 deliberately shipped one supervised worker and rejected excess jobs. Batch clients need duplicate suppression and bounded admission without launching duplicate CPU/renderer work or storing raw client keys in public status.
- **Decision:** Extend the single-process supervisor with one running job and a bounded FIFO of **two accepted jobs by default** (`--max-queued-jobs` 0–16). Limit simultaneous upload buffers to **three by default** (`--max-parallel-uploads` 1–16); each upload still has the 32 MiB byte cap. When full, reject new work with typed retryable `429 RESOURCE_LIMIT`, but allow a valid replay of an existing key even when full. Queue cancellation becomes terminal immediately; running cancellation retains ADR-018's process-tree stop and publication barrier. No multi-process queue or hosted admission claim is made.
- **Idempotency contract:** Optional `Idempotency-Key` is visible ASCII, 1–128 bytes. The server stores **only its SHA-256 digest** and a fingerprint of the input SHA-256, mode and normalized input extension in a private per-job sidecar. Same key/same request returns the original job ID and current state, including after restart or terminal failure; same key/different request returns typed `409 IDEMPOTENCY_CONFLICT`. A failed job requires a **new key** for a new attempt. A damaged sidecar or unverified persisted keyed history disables keyed admission with typed `503 IDEMPOTENCY_STORE_UNAVAILABLE`, rather than risking duplicate execution. Public job status and default stage events never contain the raw key.
- **Recovery:** In-progress/queued jobs interrupted by restart fail closed as `JOB_INTERRUPTED`; they are **not** automatically resumed with potentially changed code/config. The key-to-job mapping is reconstructed from private local sidecars, so replay of an interrupted job returns its failed status. Completed jobs remain locally readable. Cleanup/retention and cross-process locking remain ADR-014/future scope.
- **Alternatives:** Unbounded executor queue (rejected: memory/CPU pressure), keying by source hash alone (rejected: different modes or explicit retries must remain independent), and persisting raw keys in logs or status (rejected: privacy). SQLite, external brokers and distributed locks are unnecessary for one local API owner, but must be reconsidered before multi-process deployment.
- **Consequences:** Admission protects queued processing and bounded request buffers, **not** OS-level RAM; 32 MiB × 3 is only an upload-content bound, not total process RSS. A crashed API can still leave an orphan renderer as noted in ADR-018. Files persist until manual cleanup; a released job ID is not silently reused. The legacy synchronous demo route remains for compatibility, not as the queued API.
- **Validation evidence:** `python/tests/test_job_queue.py`, `python/tests/test_job_queue_http.py`, `python/tests/test_upload_slots.py`, plus process-cancellation, restart and schema tests from API-001.
- **Review trigger:** Multi-process/multi-user service, automatic retention, disk quotas, per-customer isolation, or a stronger memory/process sandbox.
